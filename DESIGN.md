## 1. Мета та опис проєкту

Це алгоритмічне ядро симуляції виробничо-логістичних процесів (Factory Simulation Engine), реалізоване мовою Python. Рушій працює без графічного інтерфейсу (headless): у ньому немає власної графіки, але через публічний API він віддає все, що потрібно для візуалізації — розташування сутностей, їхній стан і точні координати кожного предмета. Завдяки цьому поверх ядра можна прикрутити UI (наприклад, на `pygame`).

Основна мета — розробити власну архітектуру рушія без готових ігрових рушіїв (Unity, Godot) і без баз даних. Проєкт зосереджений на трьох речах:

- **модель конвеєра** з точними координатами предметів та природним виникненням заторів (backpressure) — головна тема проєкту;
- **графові алгоритми:** розрахунок порядку оновлення стрічок (зворотний BFS від стоків) та пошук зв'язних компонентів енергомережі;
- **стратегія тестування:** доведення надійності ядра через property-based, детерміновані, performance та mutation-тести, а також fault injection.

## 2. Межі проєкту (Scope & MVP)

### 2.1. Входить до MVP (In Scope)

- **Дискретний 2D-світ:** сітка $W \times H$, сутності займають прямокутні ділянки; перевірка меж і просторових колізій; доступ до клітинки за $O(1)$.
- **Конвеєри (Belts & Backpressure), пріоритет 1:** кожна стрічка має дві смуги (lane); кожен предмет має цілочисельну координату вздовж смуги (`256` одиниць на тайл); мінімальна відстань між предметами — `64` одиниці (`4` предмети на смугу тайла). Затор виникає природно: предмет не може наблизитись до попереднього ближче ніж на `64` одиниці.
- **Бокове завантаження (side-loading), пріоритет 2:** реалізовано: бічна стрічка вливається у відповідну смугу цільової на позицію `DROP_POS = 128` за наявності вільного місця.
- **Видобуток і крафт:** `Miner` (Бур) витягує ресурс із родовища; `Assembler` (Складальний автомат) виконує рецепти за часом; `Chest` (Скриня) — буфер/приймач.
- **Інсертери (Inserters):** скінченний автомат (FSM) для переносу предметів між клітинками з урахуванням таймінгів.
- **Енергомережа:** неорієнтований граф опор; поділ на мережі; пропорційне уповільнення машин при дефіциті енергії.
- **Tick-based Engine:** цикл із жорстко заданим порядком фаз і порядком обходу сутностей для гарантії детермінізму.
- **Query API для UI:** запити про розташування об'єктів і координати предметів для малювання (розділ 5).
- **JSON-серіалізація:** атомарне збереження та завантаження стану у звичайний файл.

### 2.2. Поза межами проєкту (Out of Scope)

- Графічний інтерфейс користувача (ввід/вивід обробляє зовнішній скрипт).
- Динамічне розширення карти (розмір задається при старті).
- Багатопотоковість у межах одного тіка (заважає строгому детермінізму).
- Вороги, забруднення, рідини, різні швидкості стрічок (всі стрічки мають одну швидкість).
- Спліттери, підземні конвеєри.

### 2.3. Допущення та спрощення відносно Factorio

| Аспект | Factorio | У нашому рушії | Причина |
| :--- | :--- | :--- | :--- |
| Координата предмета | дійсне число (`float`) | ціле число, `256` одиниць на тайл | уникнення помилок округлення, 100% детермінізм |
| Смуги на повороті | внутрішня смуга коротша | усі смуги однакові (`256`) | спрощення алгоритму; за візуальні заокруглення відповідає UI |
| Видача предметів | бури кладуть прямо на стрічку | лише через інсертер або конвеєр | простіший код і тестування взаємодій |
| Енергія | паливо, акумулятори | генератор із постійною потужністю | баланс гри поза темою проєкту |

## 3. Модель даних

### 3.1. Координати, напрямки, одиниці та константи

- **Сітка:** вісь `x` — вправо, вісь `y` — вниз. Клітинка `(0, 0)` — лівий верхній кут.
- **Напрямки (`Direction`):** `N = (0, -1)`, `E = (1, 0)`, `S = (0, 1)`, `W = (-1, 0)`.
- **Час:** `1 tick = 1/60` с. Усі швидкості — цілі числа.

| Константа | Значення | Зміст |
| :--- | :--- | :--- |
| `TICKS_PER_SECOND` | `60` | кількість тіків за секунду |
| `TILE_LEN` | `256` | довжина смуги в межах одного тайла |
| `ITEM_SPACING` | `64` | мінімальна відстань між предметами (4 предмети на тайл) |
| `MAX_POS` | `255` | крайня позиція в тайлі (кінець смуги), `TILE_LEN - 1` |
| `BELT_SPEED` | `8` | швидкість (`8` одиниць за тік, ~15 предм./с на 2 смуги) |
| `SAT_ONE` | `1000` | коефіцієнт задоволення енергії (`1000 = 100%`) |
| `DROP_POS` | `128` | позиція на смузі, куди інсертер або бічна стрічка кладе предмет |
| `POLE_REACH`, `POLE_AREA` | `7`, `2` | дальність дроту та радіус живлення (`5×5` навколо опори) |

### 3.2. Світ (`World`) та просторовий індекс

| Поле | Тип | Призначення |
| :--- | :--- | :--- |
| `width`, `height` | `int` | розміри світу |
| `cells` | список (довжина `W * H`) | швидкий доступ: клітинка `(x, y)` → об'єкт. Дає доступ за $O(1)$ |
| `entities` | словник `(x, y) -> Entity` | усі сутності за їхніми координатами |
| `by_type` | словник `тип -> список` | списки сутностей за типами (відсортовані для стабільного обходу) |
| `resources` | словник `(x, y) -> Deposit` | карта родовищ (руда) |
| `tick` | `int` | поточний тік симуляції |

### 3.3. Типи сутностей

| Тип | Розмір | Напрямок | Споживання | Основні дані |
| :--- | :--- | :--- | :--- | :--- |
| `belt` | `1×1` | так | — | дві смуги (`lanes`) |
| `inserter` | `1×1` | так | `13 кВт` | стан автомата (FSM), предмет у руці |
| `miner` | `2×2` | ні | `90 кВт` | вихідний буфер, прогрес роботи |
| `assembler` | `3×3` | ні | `75 кВт` | рецепт, вхідний та вихідний буфери |
| `chest` | `1×1` | ні | — | інвентар (словник ресурсів) |
| `pole` / `generator` | `1×1` / `2×2` | ні | — / генерація | належність до енергомережі |

### 3.4. Конвеєр: структури даних

Для коректного руху і можливості плавно його малювати ми не використовуємо класичні черги. Ми зберігаємо координату (`pos`) для кожного предмета на стрічці.

| Структура | Поле | Тип | Зміст |
| :--- | :--- | :--- | :--- |
| `BeltItem` | `uid` | `int` | унікальний id для плавної анімації в UI |
| `BeltItem` | `item_type` | `str` | наприклад, `"iron-plate"` |
| `BeltItem` | `pos` | `int`, `0..255` | відстань від початку тайла вздовж напрямку руху |
| `Lane` | `items` | список `BeltItem` | відсортовані за `pos` (від переднього до заднього) |
| `Belt` | `lanes` | `(Lane, Lane)` | `[LEFT, RIGHT]` смуги |
| `Belt` | `next_belt` | `Belt` або `None` | наступна стрічка (куди їдуть предмети) |

**Інваріанти (правила) смуги:**
- Предмети відсортовані за спаданням `pos`.
- `0 <= pos <= 255`.
- Відстань між будь-якими сусідніми предметами $\ge 64$ одиниці (захист від накладання).

### 3.5. Машини, інсертери та рецепти

**Одиниця `progress`:** кожного тіка до прогресу машини додається коефіцієнт енергії `sat` (від `0` до `1000`). Якщо енергії 100%, додається `1000`. Крафт завершується, коли прогрес досягає `time_ticks * 1000`. Це дозволяє пропорційно сповільнювати машини при нестачі енергії без використання дробів (`float`).

| Рецепт | Інгредієнти | Результат | Час (тіків) |
| :--- | :--- | :--- | :--- |
| `iron-plate` | `1 × iron-ore` | `1 × iron-plate` | `192` |
| `gear` | `2 × iron-plate` | `1 × gear` | `30` |

## 4. Алгоритми

### 4.1. Конвеєр виконання одного тіка (Tick Pipeline)

| Фаза | Що відбувається | Порядок обходу |
| :--- | :--- | :--- |
| 1. Power | Перебудова мереж (якщо треба). Розрахунок енергії | Мережі за ID |
| 2. Machines | Робота бурів та автоматів (заповнення буферів) | За координатами `(x, y)` |
| 3. Belts | Просування предметів по стрічках та перехід на сусідні | Від кінця до початку |
| 4. Inserters | Крок автомата (FSM) кожного інсертера | За координатами `(x, y)` |
| 5. Finalize | Очищення статусів, збільшення лічильника тіків | — |

Порядок обходу сутностей фіксований за їхніми координатами `(x, y)`. Це гарантує, що незалежно від того, в якому порядку гравець будував фабрику, результат симуляції завжди буде однаковим.

### 4.2. Оновлення конвеєрів (Backpressure)

#### 4.2.1. Просування однієї смуги

Для кожної смуги конвеєра предмети рухаються за таким алгоритмом:

1. Для переднього предмета обчислюємо `limit` (максимальну позицію, куди він може доїхати):
   - якщо наступна стрічка має предмети: `limit = r + TILE_LEN - ITEM_SPACING`, де `r` — позиція заднього (останнього) предмета на наступній смузі;
   - якщо наступна смуга порожня — обмеження немає;
   - якщо наступної стрічки немає: `limit = 255` (кінець стрічки).
2. Рухаємо предмет: `new_pos = max(pos, min(pos + speed, limit))`.
3. Для кожного наступного предмета лімітом стає позиція предмета перед ним мінус `64` (`ITEM_SPACING`).
4. Якщо `new_pos >= 256`, предмет переходить на наступну стрічку з позицією `new_pos - 256`. При боковому завантаженні (`side_load_target_lane`) передній предмет при досягненні краю тайла переходить у цільову смугу на фіксовану позицію `DROP_POS = 128` за наявності вільного місця (`can_insert_at(128)`), інакше чекає на позиції `255`.

Саме правило `new_pos = max(pos, min(pos + speed, limit))` створює природний ефект затору (backpressure): предмети фізично не можуть наїхати один на одного.

#### 4.2.2. Порядок оновлення стрічок (з кінця в початок)

Щоб ущільнений потік предметів рухався без розривів, кожна стрічка має оновлюватися після своєї наступної (куди вона віддає предмети). Тобто оновлення йде проти потоку — від приймачів до джерел.

**Алгоритм визначення порядку:**
- Знаходимо всі кінцеві стрічки-стоки (`next_belt is None`) і запускаємо від них зворотний пошук у ширину (BFS) проти напрямку руху.
- Якщо стрічки утворюють замкнене кільце, обираємо в циклі стрічку з найменшими координатами `(x, y)` як точку розриву і запускаємо зворотний BFS від неї.
- На точці розриву кільця, де наступна стрічка ще не оновлювалася в поточному тіку, переходи відкладаються до кінця фази (`deferred_straight`, `deferred_side_loads`), щоб уникнути подвійного кроку за один тік.

Такий підхід вирішує проблему заторів та циклів без складних багатопрохідних обчислень.

### 4.3. Інсертер: автомат станів (FSM)

| Стан | Умова переходу | Дія | Новий стан |
| :--- | :--- | :--- | :--- |
| `IDLE` | у джерелі є предмет | взяти предмет у «руку» | `SWING_TO_DROP` |
| `SWING_TO_DROP` | прогрес повороту завершено і ціль вільна | покласти предмет | `SWING_BACK` |
| `SWING_TO_DROP` | прогрес повороту завершено, ціль зайнята | — | `WAIT_DROP` |
| `WAIT_DROP` | ціль має вільне місце | покласти предмет | `SWING_BACK` |
| `WAIT_DROP` | ціль зайнята | чекати | `WAIT_DROP` |
| `SWING_BACK` | прогрес повернення завершено | — | `IDLE` |

### 4.4. Енергомережа

При будівництві або знесенні стовпів запускається алгоритм пошуку в ширину (BFS). Він знаходить усі з'єднані опори і формує з них компоненти зв'язності (окремі електромережі).

Щотіку для кожної мережі рахується:
- `sat = 1000`, якщо `генерація >= споживання`;
- інакше `sat = (генерація * 1000) // споживання`.

Усі машини в цій мережі отримують цей коефіцієнт і сповільнюють свою роботу.

### 4.5. Складність алгоритмів

| Операція | Складність | Коментар |
| :--- | :--- | :--- |
| Отримати об'єкт за `(x, y)` | $O(1)$ | прямий доступ до масиву `cells` |
| Додати/видалити об'єкт | $O(w \cdot h + N)$ | оновлення клітинок сутності ($w \cdot h$ — розмір) та вставка у відсортований список |
| Один крок симуляції (`tick`) | $O(B + M + I)$ | `B` — стрічки, `M` — машини, `I` — інсертери |
| Перебудова мереж | $O(P)$ | прохід BFS по стовпах (`P`) |

## 5. Публічний API бібліотеки

### 5.1. Принципи

- Команди змінюють стан; запити лише читають і повертають незмінні (`frozen`) об'єкти — UI не може випадково зіпсувати стан рушія.
- Колекції повертаються відсортованими у вигляді кортежів (`tuple`).
- Внутрішній стан використовує лише цілі числа, але API віддає `float`-координати для зручного малювання в UI.

### 5.2. Сигнатури методів

```python
class FactoryEngine:
    def __init__(self, width: int, height: int) -> None: ...

    # Команди (змінюють стан)
    def place_entity(
        self, entity_type: str, x: int, y: int, direction: str | Direction | None = None
    ) -> bool: ...
    def remove_entity(self, x: int, y: int) -> bool: ...
    def set_recipe(self, x: int, y: int, recipe_id: str | None) -> bool: ...
    def add_resource_patch(
        self, x: int, y: int, w: int, h: int, resource: str, amount: int
    ) -> None: ...
    def insert_into_chest(self, x: int, y: int, item_type: str, count: int = 1) -> bool: ...
    def drop_item_on_belt(
        self, x: int, y: int, item_type: str, lane: int = RIGHT_LANE
    ) -> bool: ...
    def tick(self, steps: int = 1) -> int: ...

    # Запити для UI (лише читання)
    def get_tick(self) -> int: ...
    def get_entity_at(self, x: int, y: int) -> EntityView | None: ...
    def get_entities(
        self, entity_type: str | None = None, rect: tuple[int, int, int, int] | None = None
    ) -> tuple[EntityView, ...]: ...
    def get_belt_items(
        self, rect: tuple[int, int, int, int] | None = None
    ) -> tuple[BeltItemView, ...]: ...
    def get_deposits(
        self, rect: tuple[int, int, int, int] | None = None
    ) -> tuple[DepositView, ...]: ...
    def snapshot(self, rect: tuple[int, int, int, int] | None = None) -> WorldSnapshot: ...
    def get_power_summary(self) -> dict[str, int]: ...
    def count_all_items(self) -> dict[str, int]: ...
    def validate_state(self) -> None: ...

    # Збереження
    def to_dict(self) -> dict: ...
    @classmethod
    def from_dict(cls, data: dict) -> "FactoryEngine": ...
    def to_json(self) -> str: ...
    @classmethod
    def from_json(cls, raw_json: str) -> "FactoryEngine": ...
    def save(self, path: str | Path) -> None: ...

    @classmethod
    def load(cls, path: str | Path) -> "FactoryEngine": ...
```

**Поля view-об'єктів:**
- `EntityView`: `entity_type`, `x`, `y`, `width`, `height`, `direction`, `network_id`, `satisfaction`, `progress`, `recipe_id`, `state`, `held_item`, `input_buffer`, `output_buffer`, `inventory`.
- `BeltItemView`: `uid`, `item_type`, `tile_x`, `tile_y`, `lane` (`0` або `1`), `pos` (`0..255`), `world_x`, `world_y`.
- `DepositView`: `x`, `y`, `resource_type`, `amount`.
- `WorldSnapshot`: `tick`, `width`, `height`, `entities`, `belt_items`, `deposits`, `power_networks`, `wire_edges`.

**Приклад використання:**

```python
entities = engine.get_entities(entity_type="assembler")
items = engine.get_belt_items()  # усі предмети на конвеєрах

for item in items:
    draw_item(item.item_type, item.world_x, item.world_y)  # див. 5.3
```

### 5.3. Перетворення координат для візуалізації

Рушій рахує все в цілих числах. Для UI позиція предмета на стрічці (`pos` від `0` до `255`) перетворюється у світові координати `world_x`, `world_y` за формулою лінійної інтерполяції:

$$P = \text{центр\_тайла} + \text{напрямок} \cdot \left(\frac{\text{pos}}{256} - 0.5\right) + \text{зсув\_смуги}$$

де `зсув_смуги` — перпендикулярний зсув для лівої/правої смуги (`0.25` / `0.75` у межах тайла). Це дозволяє UI малювати гру в 60 FPS, просто запитуючи координати, навіть якщо бекенд рахує логіку повільніше.

## 6. Формат збереження (Persistence)

Стан зберігається у структурованому JSON-файлі. Дані відсортовані за координатами, тому однаковий стан завжди дає ідентичний файл. Запис виконується атомарно: спочатку у тимчасовий файл з `fsync`, потім він замінює основний через `os.replace`, тому збій запису не пошкоджує попереднє збереження. Усі помилки вводу-виводу, синтаксису JSON чи валідації схеми піднімають виняток `PersistenceError`.

```json
{
  "version": 1,
  "width": 64,
  "height": 64,
  "tick": 1200,
  "next_item_uid": 42,
  "resources": [
    {"x": 10, "y": 10, "resource_type": "iron-ore", "amount": 500}
  ],
  "entities": [
    {
      "type": "belt",
      "x": 14,
      "y": 11,
      "direction": "E",
      "lanes": [
        [],
        [{"uid": 17, "item_type": "iron-ore", "pos": 191}]
      ]
    },
    {
      "type": "assembler",
      "x": 21,
      "y": 10,
      "recipe_id": "iron-plate",
      "input_buffer": {"iron-ore": 1},
      "output_buffer": {},
      "progress": 96000
    }
  ]
}
```

## 7. Стратегія тестування

### 7.1. Property-Based Testing (бібліотека `hypothesis`)

За допомогою `hypothesis` генеруються випадкові фабрики і послідовності дій. Перевіряються такі інваріанти:
- **Облік предметів:** без рецептів кількість предметів стала — вони не зникають і не з'являються з нічого (зокрема на стику заторів). З рецептами зберігається сумарна маса заліза за ваговим оракулом `ITEM_MASS` (`iron-ore = 1`, `iron-plate = 1`, `gear = 2`): `маса у світі + залишок руди в родовищах = const`.
- На стрічці предмети ніколи не накладаються один на одного (відстань завжди $\ge 64$).
- Предмет за один тік не може проїхати більше, ніж дозволяє швидкість стрічки (виняток — боковий вхід на фіксовану позицію `DROP_POS = 128` та поява предмета від інсертера).
- Після збереження і завантаження стан залишається абсолютно таким самим.
- Якщо фабрика стоїть (немає ресурсів / все забито), то навіть після 1000 тіків нічого не змінюється.

### 7.2. Детерміноване та Unit тестування

- **Незалежність від порядку:** розміщення сутностей у порядку `[A, B, C]` і `[C, A, B]` дає однаковий результат симуляції (за відсутності колізій простору).
- **Детермінізм симуляції:** два незалежні екземпляри рушія з однаковими командами після $N$ тіків мають однаковий стан (побітово однаковий JSON).
- **Тести заторів:** заповнена на 100% стрічка розблоковується коректно без втрати предметів.
- **Дефіцит енергії:** при забезпеченні мережі на 50% автомат крафтить деталь рівно вдвічі довше.

### 7.3. Performance, покриття, мутаційне тестування та Fault Injection

- **Performance:** цільовий показник — обробка `2500` сутностей за `< 16,6` мс на один тік.
- **Покриття:** `pytest-cov`, покриття гілок (branch coverage) не менше `90%` для критичних модулів логіки (`belts.py`, `persistence.py`, `views.py`, `engine.py`).
- **Мутаційні тести (`mutmut`):** штучна зміна коду (наприклад, заміна `<` на `<=`). Тести повинні «впасти», щоб довести, що вони дійсно перевіряють логіку.
- **Fault Injection:** імітація збою диска (наприклад, «диск повний») під час `save()`. Рушій не падає, стан у пам'яті лишається цілим, а попередній файл збереження не пошкоджується.

## 8. Структура проєкту

Проєкт оформлюється як стандартний Python-пакет:

| Модуль | Відповідальність |
| :--- | :--- |
| `constants.py` | усі налаштування швидкості, таймінгів та розмірів |
| `world.py` | просторовий індекс, сітка, родовища |
| `entities.py` | базові класи для бурів, інсертерів, автоматів |
| `belts.py` | логіка руху конвеєрів та розрахунок заторів |
| `power.py` | пошук мереж (BFS) та розрахунок енергії |
| `views.py` | read-only об'єкти для API та математика для UI |
| `persistence.py` | збереження та завантаження JSON |
| `engine.py` | головний фасад (клас `FactoryEngine`) та пайплайн тіка |
| `tests/` | усі тести (unit, hypothesis, benchmark) |
